## Learnings

- Symmetry reduction is key: 758 pipes -> 273 unique types. GPU kernels work on types, not individual pipes.
- forge-ffi custom kernel API (`forge_kernel_compile` + `forge_pipeline_dispatch_1d`) is an exact fit. The `custom_kernel.c` example confirms buffer binding pattern: `device const float*` for inputs, `device float*` for outputs.
- Params buffer packing: `[n, target, max_waste, inv_0, ..., inv_n-1]` as float32 array. For n=273, only 1104 bytes. Passed as a `device const float*` buffer binding.
- Metal atomic counter (`atomic_uint` with `atomic_fetch_add_explicit`) is the standard pattern for variable-length GPU output. Pre-allocate 4M output slots (worst case ~1M valid patterns for n=273, waste=5).
- Solution dict format must match exactly: `{'pattern_type', 'length_indices', 'pipe_lengths', 'total_length', 'waste', 'num_welds'}`. The `export_to_excel()` function accesses `solver.raw_lengths`, `solver.precision`, `solver.unique_lengths` so `GPUPipeOptimizer` must expose all of these.
- GUI worker thread pattern: read all tkinter vars in main thread, pass as dict to worker. GPU solver integrates identically.
- forge-ffi dylib must be built first: `cargo build -p forge-ffi --release` in `~/gpu_kernel/metal-forge-compute/`.
- CPU fallback is essential: pattern gen can fall back to Python loops, solver can fall back to ILP. No hard GPU dependency.
